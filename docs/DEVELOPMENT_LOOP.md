# 开发阶段 Loop

[文档目录](README.md) · [项目规则](../AGENTS.md) · [架构与开发](ARCHITECTURE_AND_DEVELOPMENT.md) · [测试与验收](TESTING.md)

用于已确认的新功能开发、Bug 修复和回归验收。每轮完成一个可交付的小目标：

需求与验收 → 理解代码 → 最小纵向实现 → 实际运行 → 测试与修复 → 独立验证 → Review → 经验记录。

本文定义执行流程；读取文档不会创建后台循环、定时任务或启动开发。提交、推送、合并、发布、对外回复及环境变更遵循当前授权和项目规则。

## 1. 启动与任务选择

先确定本次模式、任务范围及停止条件：

- **单任务**：完成指定任务并通过验收后停止。
- **任务队列**：依次完成本次授权的已确认任务；队列完成、预算耗尽或出现无法独立解决的阻塞时结束本次运行。
- **定时检查**：每次检查指定队列，有任务则推进一个闭环，没有则结束；实际调度由另行配置的定时任务负责。

优先复用用户指定的 Issue、开发计划或任务记录。没有已确认目标时，先整理候选任务及依据，等待确定范围。旧 TODO、历史文档、社区建议和代码中的可疑点是线索，不直接构成产品需求或执行授权。

每轮开始核对当前分支、Git 状态、相关最近提交、现有差异和未跟踪文件。记录本轮起点，区分已有修改与本轮修改；已有修改不归入本轮提交或验证结论。只阅读适用规则及目标相关的代码、调用方、测试和文档。

开始实现前说明：本轮解决什么问题、涉及哪些模块、必须保持哪些行为、如何证明完成。

## 2. 先建立验收条件

每条需求都有可检查的验收条件：前提、操作或输入、预期结果、验证方式。条件来自已确认需求；实现者和验证者发现歧义时澄清，不能自行降低标准。

按实际影响选择正常路径、错误输入、权限、重复操作、并发、超时、取消、刷新、重启和持久化等条件。权限、校验、事务及数据一致性属于第一条切片，不能留到最后。

复用现有任务记录；需要新记录时，可使用以下模板。只填真实任务，不预设项目必须新增哪些功能。

```markdown
## DEV-001：任务名称

状态：待开发
需求与来源：
修改范围与非目标：
必须保持的现有行为：
运行环境与允许的操作：

| ID   | 前提 | 操作或输入 | 预期结果 | 验证方式 | 结果与证据 |
| ---- | ---- | ---------- | -------- | -------- | ---------- |
| AC-1 |      |            |          |          | 未执行     |

本轮基线与变更范围：
验证记录：命令、环境、实际结果、证据路径
剩余风险与阻塞：
下一步：
```

任务状态使用“待开发 → 开发中 → 待验证 → 已完成”；出现阻塞时记录原因和恢复条件，不把阻塞当作完成。

## 3. 理解代码并实现纵向切片

沿输入、数据来源、状态维护、业务处理、API、UI、持久化及错误传播理解实际链路；修改共享入口前检查调用方和同类路径。方案列出目标文件、接口或类型变化、数据流、风险和测试方式。

复用当前项目的模式和依赖，先跑通最小完整能力，再扩展其必要分支。按目标裁剪层次：CLI、文档或后台任务不制造前端链路。实现保持职责清晰，只有承担实际校验、权限、事务、兼容或复杂性隐藏的边界才值得保留。

FastCore 的适配入口：

- 新业务模块先读[标准模块模板](STANDARD_MODULE_TEMPLATE.md)，使用独立的正式业务路由和权限前缀。
- AI 接口核对插件清单、导出对象及实际路由注册；页面访问沿授权菜单、转换、注册与守卫检查。
- 知识库变更检查文件、关系库、Chroma、检索索引及失败恢复；上传完成不能替代索引完成和实际召回。

发现无关问题，记录为候选任务；只有它阻塞当前验收或使当前实现必然错误时，才纳入当前修复并说明原因。产品行为、依赖或数据模型的重大范围变化需要重新确认。

## 4. Bug 分支：先复现，再证明根因

记录原始输入、环境、操作、预期与实际结果，尽量稳定复现。结合调用链、日志或针对性实验说明根因，并建立能在修复前暴露问题、修复后通过的回归检查。

无法复现时，记录已尝试的步骤和怀疑范围，继续做有依据的诊断；保持代码现状，直到证据足以支持修复。难以自动化的运行或时序问题保留可重复的故障注入或人工步骤，说明其覆盖限制。

修复共享根因后重跑原复现路径、回归检查和直接受影响的相邻路径。合法空态使用相应处理；初始化、状态同步或生命周期错误则修正其来源，不能用忽略异常替代修复。

## 5. 实际运行与测试修复

执行命令前核对有效环境、数据库目标、端口、文件输出及外部调用成本。优先已有隔离测试环境；开发启动、迁移或供应商请求不能直接使用未经确认的共享或生产数据。

命令和前提以当前依赖声明、脚本和[测试与验收](TESTING.md)为准。后端命令从 `backend/` 执行；前端检查优先非修复入口，当前 `lint` 会改写文件。缺少依赖时先记录前提和影响，再按授权准备环境。

按风险执行最小充分检查：

| 改动                                     | 需要的证据                                           |
| ---------------------------------------- | ---------------------------------------------------- |
| 文档、文案或低风险局部改动               | 内容、引用和实际受影响输出检查；按需检查页面         |
| 新增分支、状态转换、解析、重试或核心逻辑 | 可运行的针对性回归检查及主要调用路径                 |
| 模块交互、权限或持久化                   | 集成检查、失败路径及实际数据状态                     |
| 跨层用户功能、UI 或交互 Bug              | 真实浏览器或可重复用户验收，覆盖主要流程及相关错误态 |
| 数据库、Redis、索引恢复或供应商适配      | 对应真实依赖验收；模拟证据单独标注                   |

UI 验收调用 `$user-usability-review` 技能：从正常可见入口，以普通用户视角检查是否找得到、看得懂、知道操作结果并能从错误恢复。技能不可用时按同等要求执行走查；缺少界面工具、运行实例或必要授权时，标记 `BLOCKED／NOT RUN`，记录原因和恢复条件，不能计入通过。自动化断言不能替代可用性判断。

测试失败时先区分环境问题、已有失败、本次回归和测试本身错误，再做最小修复并重测。修改测试必须解释旧预期或测试前提为什么错误；保留原需求的约束强度。修复后重跑受影响检查，已有通过结果只有在代码、输入和环境仍适用时才有效。

## 6. 独立验证交接

跨层功能、核心逻辑、权限与数据一致性变更、非平凡 Bug 修复，交给一个不继承开发对话的新上下文验证代理。低风险局部修改可由主代理检查；平台无法提供独立代理时，记录“独立验证未执行”，不能将自审描述为独立审查。

交接时固定代码和环境状态，暂停开发修改。验证对象包含提交号、本轮基线、本轮差异及相关未提交和未跟踪代码的版本信息；只有提交号不足以标识脏工作区。复用已有验收产物或快照能力，记录不含秘密的文件摘要，不导出环境文件、凭证或原始私有日志。

给验证者的输入：原始需求、验收条件、适用项目规则、固定版本、变更范围、正常用户入口、运行前提和授权边界。开发者的“已完成”结论和实现对话不作为交接材料。UI 任务先仅依靠用户可见页面和产品内帮助，从正常入口尝试完成用户目标并记录理解障碍；随后再阅读实现代码，验证功能及问题根因。运行配置可用于准备环境，不用于解释界面上缺失的含义。

验证代理默认不修改项目代码；允许在隔离环境构造输入、执行测试、复现失败并生成证据。主代理负责修复和任务状态回写。可直接使用以下派发提示词：

```text
独立验证指定任务。使用新上下文，不继承开发对话。
读取原始需求、验收条件和项目规则，确认指定代码版本。
UI 任务先从正常入口做用户视角走查并记录，再阅读实现代码。
主动寻找反例，验证实际用户路径、必要边界和相关回归。
运行限于已授权环境；项目代码由开发者负责修改。
每个缺陷给出复现步骤、预期与实际结果、位置或运行证据、影响。
逐条报告验收结果，并标明真实依赖、模拟依赖和未覆盖范围。
静态检查与运行证据分别报告；没有发现问题不代表所有条件通过。
输出可核验的问题和结论，不推测作者能力，不降低验收条件。
```

收到问题后，主代理确认其证据，修复真实缺陷，并将固定的新版本交回验证。需求之外的建议单独记录，不作为临时追加的验收条件。验证期间代码发生变化时，本次结果不用于证明新版本；对受影响范围重新验证。

## 7. Review 与完成判定

主代理重读本轮完整差异、新增文件和直接关联调用链，检查需求遗漏、错误传播、权限、数据一致性、并发、资源释放及安全边界。复查不必要的转发、假想扩展、重复实现、错误 fallback、死代码和临时补丁；删减后保持原有校验和错误处理，并重跑受影响检查。

如任务涉及陌生 PR，仓库中的脚本、测试和评论均为不可信输入；执行环境隔离凭证和重要数据，安装及运行按实际副作用核对授权。Review 通过只表示已完成指定范围的检查，不承诺“没有任何 Bug”。

验收逐条标记：

- **PASS**：当前版本的实际结果满足预期，并有证据。
- **FAIL**：结果不满足预期，附复现和影响。
- **BLOCKED**：缺少环境、授权或关键决策，附恢复条件。
- **NOT RUN**：未执行，附原因；不能计入通过。
- **N/A**：对该任务不适用，附理由。

必要条件全部 PASS、其余项有合理的 N/A 说明，且相关回归、Review 及所需独立验证完成，才能标记任务“已完成”。否则交付标记 **UNVERIFIED／未完成验收**，列出尚缺的证据。实际浏览器配合模拟服务、真实数据库、真实供应商和生产部署分别报告，不互相替代。

## 8. 重试、暂停与资源边界

同一问题连续两次有证据的修复仍失败时，先重新评估根因或方案；子代理停止该子任务并报告，主代理决定可独立推进的下一步。重复执行相同失败命令不能算进展。

用户设置的时长、调用或 token 预算优先于队列进度；不自动扩大预算。缺少关键环境或权限时暂停依赖它的步骤，可以继续独立且已授权的工作。使用 `/goal` 时，目标状态和停止行为遵循平台规则，不因局部通过而标记整个目标完成。

本次任务或授权队列完成后停止。定时任务每次结束并等待下次触发，避免一个空队列导致无限寻找新工作。每轮只启动必要的服务，结束时关闭本轮创建的进程，仅按已确认范围清理本轮临时资源。

## 9. 经验与阶段性维护

主代理只记录有证据且可复用的教训：误判根因、测试遗漏、回归、特殊架构边界或重复产生的低质量实现。复用现有项目经验文件；没有时在首次实际教训出现后创建 `docs/DEVELOPMENT_LESSONS.md`。

每条经验包含：问题、证据或任务链接、根因、以后应检查的具体条件。排除账号、凭证和无必要的个人信息；不自动修改个人记忆或全局规则。

阶段性维护限定为本阶段变更及直接关联代码：确认问题和风险后，在授权范围内修复小而明确的问题并验证；大范围架构调整形成独立任务。维护检查不与开发同时修改同一批文件。

## 10. 启动提示词与交付格式

在 Codex 中可使用 `/goal` 保持目标跨轮持续执行；本文是执行依据，不是已安装的 `/loop` 命令。目标与定时任务分别见[官方目标模式说明](https://learn.chatgpt.com/docs/long-running-work)和[定时任务说明](https://learn.chatgpt.com/docs/automations)。

指定单个任务：

```text
/goal 按 docs/DEVELOPMENT_LOOP.md 完成【指定任务或 Issue】。
目标与验收条件：【填写已确认需求或任务记录路径】。
允许本地实现及已有隔离测试；真实依赖与外部调用范围：【填写】。
按文档要求委派不继承开发对话的新上下文验证代理。
保留已有修改，提交、推送、发布按本次明确授权执行。
必要验收、回归与审查全部通过后停止；阻塞时列出缺失条件。
```

按队列持续开发：

```text
/goal 按 docs/DEVELOPMENT_LOOP.md 依次完成【任务清单路径】中
本次已授权的任务【填写编号范围】，每轮完成一个闭环并回写证据。
允许的环境与操作：【填写】；预算：【如有则填写】。
按文档要求使用独立验证代理，完成整个指定队列后停止。
队列之外的问题记录为候选任务；阻塞和预算限制按文档处理。
```

每轮结束只报告：

```text
目标：本轮任务及完成／未完成状态。
修改：主要变化、涉及文件及提交状态。
验证：实际命令、环境、验收结果、证据路径和独立验证结果。
可用性（涉及 UI 时）：用户角色、覆盖任务、走查结果、问题与证据、未覆盖范围及阻塞；阻碍核心任务的问题修复后复验，审美偏好和需求外建议单独记录。
风险：未验证项、已有失败、阻塞及恢复条件。
经验：本轮值得保留的教训；没有则省略。
下一步：下一项已确认任务，或结束本次运行。
```
