# OAuth 账号绑定

OAuth 只允许登录已由管理员明确绑定的内部账号，不自动注册、创建账号或迁移绑定。绑定使用已有的 `sys_user` 数据库字段；无需新增表、迁移、依赖、前端或公开绑定接口。

## 身份字段

| 提供方 | `sys_user` 字段 | 存储内容 |
| --- | --- | --- |
| GitHub | `github_login` | 已认证 `/user` 响应中正整数 `id` 的十进制字符串，例如 `"123456"` |
| Gitee | `gitee_login` | 已认证 `/api/v5/user` 响应中正整数 `id` 的十进制字符串 |
| 微信 | `wx_login` | 用户资料包含 `unionid` 时使用完整 `unionid`；没有该键时使用完整 `openid` |
| QQ | `qq_login` | 令牌对应身份查询得到的完整 `openid` |

字段名为历史命名：GitHub/Gitee 存的是不可变数值用户 ID，不是可修改、可回收的 `login`、昵称、邮箱或内部用户名。提供方响应的 `id` 必须是 JSON 正整数，字符串、布尔、浮点、零、负数和缺失值均拒绝。

四个字段均为可空 `String(32)`，种子数据为 `NULL`。身份必须是 1～32 字符的原始字符串，不能含空白或不可打印字符。不进行截断、字符替换、大小写折叠、去空白、哈希或其他有损变换；超长或无效身份直接拒绝。不同提供方只查询各自字段，相同字符串不会跨提供方匹配。

微信还要求用户资料的 `openid` 与令牌对应 `openid` 精确一致，且资料没有错误码。若响应含 `unionid` 但其为空、无效或超长，拒绝登录，不回退 `openid`。若原来只绑定了 `openid`，后来响应提供 `unionid`，管理员需重新核验并显式修改绑定，不会自动尝试另一个标识。QQ 用户资料须明确返回成功的 `ret=0`（兼容字符串 `"0"`）。

## 查找与兼容性

数据库先按对应字段筛选候选，然后用 Python 字符串相等比较完整身份，避免 MySQL 不区分大小写、重音或尾随空格的排序规则扩大匹配。同一提供方有多条完全相同绑定时拒绝登录，不选取第一条；冲突检查也包含停用或软删除账号，以免它们掩盖重复绑定。唯一绑定指向软删除账号时不可登录，停用账号仍由回调现有状态检查拒绝。

旧版通过 `oauth_{provider}_{subject}` 清洗、截断后查找 `username`。该规则会使不同外部身份匹配同一内部账号，已经删除。即使内部账号名称碰巧完全符合旧规则，也必须补充真实身份绑定才能使用 OAuth；不会尝试旧 `oauth_*` 用户名、提供方 `login`、昵称、邮箱或任何自动绑定迁移。旧有字段若人工填写过用户名，也必须先核验再改成上表所述真实身份。

密码登录及内部账号名称不因本修复改变。OAuth state 消费、一次性 ticket、成功后的登录时间提交和会话创建保留原有流程，回调函数及其返回元组形状保持兼容；GitHub/Gitee 资料函数返回元组第一项改为数值 ID 的字符串。现有用户响应仍可包含这四个字段，用户创建、编辑和个人资料写入接口不提供绑定能力。

## 管理员显式绑定

当前没有绑定 UI 或公开 API。管理员使用现有数据库管理流程写入对应字段：

1. 核实部署环境、数据库及内部账号的稳定主键 `sys_user.id`，并核实该账号应当拥有此外部身份。通过可信的提供方认证过程取得上表身份；不要根据用户名、显示名称、邮箱、旧截断账号名推断归属，也不要把访问令牌写入绑定字段或日志。
2. 核对提供方应用及其身份命名空间。微信/QQ 的 `openid` 必须来自当前部署使用的应用。更换应用或微信身份类型时重新核验；数据库字段不另存应用 ID 或身份类型，不能自动跨应用或跨 `unionid`/`openid` 迁移。
3. 在受控事务中检查对应字段的全部现有值，包含软删除、停用账号。按完整原始字符串精确比较，确认没有其他账号持有同一提供方身份。数据库本身没有这些字段的唯一约束，因此管理写入应串行执行，避免并发绑定冲突。
4. 仅更新目标账号的对应字段。以下是绑定 GitHub 的参数化 SQL 形状，须由管理工具绑定参数；其他提供方使用表中固定字段，禁止把不可信输入当列名。

   ```sql
   UPDATE sys_user
   SET github_login = :subject
   WHERE id = :internal_user_id
     AND is_deleted = false
     AND github_login IS NULL;
   ```

   校验受影响行数为 1，重新读取并精确确认字段值及归属后提交。已有值需替换时先核验原绑定，使用当前值的精确检查防止覆盖其他管理操作。缺少唯一约束不能以此语句替代第 3 步。

5. 从普通登录入口重新发起对应提供方 OAuth，确认登录到了预期内部账号。解除绑定时，经授权把该字段设为 `NULL`；这会阻止以后使用该身份登录，但不是会话吊销操作，已有会话需按既有管理流程处理。

本文没有执行任何真实数据库写入，也没有提供自动绑定或批量迁移脚本。

## 可重复回归

从 `backend/` 执行：

```bash
.venv/bin/pytest -q tests/test_oauth_identity_binding.py \
  tests/test_audit_regressions.py::test_bound_oauth_login_keeps_user_and_commits_timestamp \
  tests/test_auth_session.py
```

新增测试使用临时文件 SQLite 和实际 SQLAlchemy 用户模型、查询及提交；绑定字段在测试库中使用 `NOCASE` 排序规则，以验证 SQL 大小写不敏感时 Python 精确比较仍生效。测试覆盖旧长用户名碰撞、完整绑定、重复与错配、提供方隔离、账号状态、非法身份与资料、数值 ID 不受改名/用户名回收影响，以及真实绑定查找到会话创建的回调路径。

最初 101 个新增用例在修复前为 **94 失败、7 通过**，其中四个提供方的旧长用户名碰撞均能复现错误登录；修复后这些用例通过，之后补充了更多资料与回调边界用例。回调测试模拟提供方 HTTP 响应和令牌兑换，Redis 使用内存替身；不连接真实提供方或真实数据库。SQLite `NOCASE` 是排序规则回归证据，不等同于真实 MySQL/PostgreSQL 或真实第三方授权端到端验收。
