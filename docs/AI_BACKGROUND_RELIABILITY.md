# AI 后台任务与上传文件恢复

本说明对应 2026-10-22 的可靠性补充，替代架构修复报告中“记忆满载跳过”和“提交异常文件只保留、不回收”的行为。后端仍使用现有 SQL 数据库及模块生命周期，无新增消息队列依赖。

## 记忆提取

`ChatSessionCRUD.append_run_crud()` 将聊天记录和 `ai_memory_extraction_job` 一起写入调用方事务。事务失败时两者一起回滚；成功后即使进程退出，待提取任务仍在数据库中。流式和非流式聊天共用该入口，日志分析与未持久化的临时回答不产生任务。

每个后端进程启动 4 个 worker，满载时任务等待，不再跳过。不同用户可以并行，同一用户的已提交任务按 ID 顺序处理；认领时通过用户行锁及当前读检查已有租约，避免提交可见性不同造成同用户重叠执行。

执行过程：

1. 短事务认领任务，增加尝试次数并写入唯一 token 和 120 秒租约。
2. 短读事务检查源会话和用户仍存在、未删除，读取已有记忆，随后释放数据库连接。
3. 在数据库事务之外调用模型，正常执行上限 90 秒。
4. 短写事务再次核验 token、租约和源数据，将记忆修改与任务删除一起提交。

模型异常、超时、无效提取结果或数据库写入失败会保留任务。重试间隔从 2 秒开始递增，最多 300 秒，不因重试次数达到上限而丢弃。没有值得提取的信息时，模型正常返回 `{"actions":[]}`，任务可以完成。

正常关闭会取消模型等待，等待已开始的短 SQL 操作收尾并释放本进程租约。强制退出时，其他进程可在租约到期后接管。已失去 token 的旧执行者不能写入记忆；记忆修改和任务删除原子提交，提交回执丢失不会重复应用同一次已完成的修改。外部模型调用本身仍可能因重试而发生多次。

用户删除会话时，同事务删除该用户对应的待提取任务；已在模型调用中的任务返回后也不能重新写入。成功任务立即删除，不长期保留额外的对话副本。

迁移脚本：`backend/app/alembic/versions/20261022_memory_jobs.py`。正常启动沿已有锁和 Alembic 流程部署；本轮仅在隔离数据库执行迁移，没有修改已有开发或生产数据库。迁移不补提取历史对话。

排查积压可只查询任务元数据，避免导出对话正文：

```sql
SELECT id, user_id, session_id, attempts, available_at, lease_until
FROM ai_memory_extraction_job
ORDER BY id;
```

4 是每进程工作并发，仍需结合实际供应商延迟与配额调优。供应商长期不可用时，任务会积压，同一用户后续任务等待较早任务重试；本轮未新增管理界面或人工重试 API。

## 知识库上传文件

新上传文件使用 `kb-<知识库ID>-<随机值>.<后缀>`，替换文件使用 `doc-<文档ID>-<随机值>.<后缀>`。名称记录用于恢复的事务归属，不改变上传和授权下载接口。

写文件之前，上传持有知识库行锁，替换持有文档行锁，直到提交或回滚。提交开始之前发生明确失败时，仍立即补偿本次新文件；提交开始之后发生异常时，先保留文件，交给后续核对处理。

知识库的生命周期 worker 分别执行索引恢复与上传文件恢复，互不阻塞。文件恢复每 15 秒检查一次，默认只处理超过 3600 秒的新格式文件：

1. 从文件名确定事务归属。
2. MySQL/PostgreSQL 用 `FOR UPDATE SKIP LOCKED` 获取归属行锁；忙碌上传跳过，下轮再检查。SQLite 使用写事务作为相同屏障。
3. 取得屏障后才读取数据库引用，包含所有文档的 `file_path`、`pending_file.file_path`、`file_cleanup_paths`，也包含软删除记录。
4. 无任何引用时才删除；删除失败留待下轮重试。仍被引用的文件保留，由已有索引或删除恢复流程处理。

文件年龄只决定何时检查，安全依据是事务锁和锁后引用核对。长时间上传、提交迟迟未返回或数据库已提交但回执丢失，都不会单凭文件年龄被删除。部分文件写入后进程崩溃，也可在事务锁释放后恢复清理。

清理只处理知识库存储根目录中的受支持普通文件，核验文件身份，不跟随文件或根目录符号链接，使用 POSIX 目录文件描述符限制删除位置。

历史纯 UUID 文件没有可靠事务归属，归属行被物理删除的文件也无法取得屏障，均保守保留；这类存量文件需另行离线核对。本轮没有清理已有业务文件，也没有新增全盘文件扫描或 Windows 删除实现。

## 设计与验收

适配 CodeVault 的 `scheduler-reconciliation` 和 `bounded-async-dispatcher` 不变量：持久数据是任务事实来源，进程内 worker 只负责执行；满载等待；用租约 token 隔离过期执行者。沿用本项目的 SQL 认领及模块生命周期，没有引入独立调度框架。

专项回归：`backend/tests/test_memory_queue.py` 与 `backend/tests/test_upload_reconciliation.py`。真实依赖入口为 `backend/integration/runtime_acceptance.py`，新增检查在 `integration/reliability_checks.py`。

真实验收使用临时 MySQL/Redis、生产生命周期、实际 HTTP 认证和聊天持久化、真实事务锁和磁盘文件；模型回答是本地确定性替身。还通过独立进程的 SIGKILL 检查记忆租约接管和重复重启。实际执行结果见本轮交付记录，不以脚本存在代替运行通过。
